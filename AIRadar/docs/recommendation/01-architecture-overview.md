# 추천 시스템 아키텍처 개요

> **대상 독자**: 개발자, 기획자
> **읽는 데 걸리는 시간**: 약 10분
> **전제 지식**: REST API 기초, 데이터베이스 기초

이 문서는 AI-Radar 추천 시스템이 어떻게 동작하는지, 왜 이렇게 설계되었는지를 설명합니다.

---

## 왜 이런 구조인가

추천 시스템은 두 가지 상충하는 요구사항을 동시에 만족해야 합니다.

- **실시간성**: 방금 북마크한 기사의 관심사가 다음 추천에 즉시 반영되어야 합니다.
- **정확성**: 수많은 사용자의 행동 패턴을 학습해 "나와 비슷한 사람들이 좋아한 기사"를 제공해야 합니다.

이 두 요구사항을 단일 시스템으로 해결하면 어느 쪽도 제대로 되지 않습니다. 그래서 AI-Radar는 **2-Layer 구조**를 선택했습니다.

---

## 전체 구조

```
사용자 행동 (조회, 검색, 북마크)
         │
         ▼
┌─────────────────────────────────────┐
│  실시간 레이어 (Spring Boot + Redis) │
│                                     │
│  이벤트 수신 → Redis 프로파일 즉시  │
│  업데이트 → 키워드 매칭 추천        │
└──────────────┬──────────────────────┘
               │ 동시에
               ▼
     search_logs 테이블 (PostgreSQL)
               │
               │ 매일 새벽 3시 (Airflow DAG)
               ▼
┌─────────────────────────────────────┐
│  배치 레이어 (Spark ALS)             │
│                                     │
│  30일치 로그 → 협업 필터링 학습 →   │
│  user_recommendations 테이블 저장   │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│  추천 서빙 (RecommendationService)   │
│                                     │
│  1. Redis 캐시 확인 (30분 TTL)       │
│  2. ALS 결과 + 키워드 매칭 결합      │
│  3. 재랭킹 후 응답                   │
│  4. 결과 없으면 인기 기사 폴백       │
└─────────────────────────────────────┘
```

## 실시간 레이어: Redis 프로파일

### 어떻게 동작하나

사용자가 기사를 조회하거나 북마크하면 Spring Boot가 이 이벤트를 받아 **즉시** Redis에 기록합니다. API 응답은 이 처리를 기다리지 않습니다 (fire-and-forget).

Redis에는 사용자별로 다음과 같은 Hash가 저장됩니다.

```
key: user:{userId}:profile
type: Hash

kw:AI              → 15.5    (AI 관련 기사를 많이 봤을수록 높음)
kw:HBM             → 8.0
kw:반도체            → 6.5
art:news_001       → 1.0    (이 기사를 조회함)
art:news_002       → 5.0    (이 기사를 북마크함)
ppv:paper_001      → 1.0    (이 논문을 조회함)
bm:news_002        → 1      (북마크가 프로파일에 반영된 횟수 — 북마크 삭제 시 되돌릴 근거)
bmkw:news_002      → "AI␟HBM"  (그때 반영한 키워드, 구분자 U+001F)
rev                → 12      (캐시 키 무효화 횟수 — 추천 계산 중 무효화가 끼어들었는지 확인하는 용도. 북마크는 두 캐시를 지우므로 2 증가)
last_active        → "2026-03-20T14:30:00"
```

TTL: **30일** — 30일간 활동이 없으면 프로파일이 만료됩니다.

### 이벤트별 가중치

| 이벤트 | 가중치 | 설명 |
|--------|--------|------|
| 기사 조회 | 1.0 | 체류 시간과 무관하게 동일 가중치 (클릭도 체류 0으로 발송되어 반영됨) |
| 검색 | 2.0 | 검색은 명시적 관심 표현 |
| 좋아요 | 3.0 | **미구현** — 아래 참고 |
| 북마크 | 5.0 | 가장 강한 저장 의도 (북마크를 삭제하면 프로파일이 기록해 둔 만큼만 되돌림). 이벤트 1건당 가중치이며, 현재 프론트는 북마크 버튼 한 번에 `article-bookmark`를 두 번 보내므로(`TimelineItem.tsx`의 `trackBookmark` + `bookmarkApi.addNewsBookmark`) 실제로는 클릭당 10.0이 반영되고 `bm:`도 2가 됩니다. 삭제 시에는 기록된 횟수만큼 되돌리므로 짝이 맞습니다. |

> **체류 시간 필터링은 하지 않습니다**: 백엔드는 `dwellTimeSeconds`를 받지만 가중치 계산과 캐시 무효화에 사용하지 않고, 수신한 조회 이벤트를 모두 반영합니다. 실제 프론트가 보내는 조회 이벤트는 기사 클릭(`trackArticleClick`, 체류 0)뿐이라, 체류 시간 기준 필터를 도입하려면 프론트의 클릭 신호와 함께 결정해야 합니다.

> **좋아요는 아직 구현되지 않았습니다.** 백엔드에는 좋아요 엔드포인트와 `ARTICLE_LIKED` 이벤트 기록이 없습니다. 다만 프론트(`eventService.ts`)는 `/events/article-like`를 호출하고, Spark ALS 배치(`CollaborativeFilteringJob`)는 `ARTICLE_LIKED`에 가중치 3.0을 정의해 두었습니다. 지금은 호출해도 처리하는 핸들러가 없어 반영되지 않습니다.

> **북마크 삭제**: 북마크를 삭제하면 프로파일이 **북마크 시점에 기록해 둔 만큼만** 되돌립니다. 북마크할 때 `bm:{articleId}`(반영 횟수)와 `bmkw:{articleId}`(그때 반영한 키워드)를 함께 기록하고, 삭제 시 `bm:`에서 삭제된 북마크 수만큼을 원자적으로 차감한 뒤 그 횟수 × 5.0을 `art:{articleId}`와 `bmkw:`의 키워드 `kw:` 가중치에서 뺍니다. 0 이하가 된 필드는 제거하고 추천 캐시를 무효화합니다. 조회·검색 등 다른 이벤트로 쌓인 값은 유지됩니다.
>
> 기록이 없으면 아무것도 되돌리지 않습니다. 프로파일이 30일 비활성으로 만료된 뒤에 삭제하는 경우, 또는 이 기록 기능이 도입되기 전에 만든 북마크는 기록이 없어 가중치가 그대로 남습니다 (`search_logs`의 행 수를 그대로 믿고 빼면 조회·검색으로 쌓은 값까지 지워질 수 있기 때문입니다). 같은 삭제가 동시에 두 번 들어와도 차감 총량은 기록된 횟수를 넘지 않습니다. 프로파일 되돌리기는 DB 삭제가 커밋된 뒤 비동기로 처리됩니다.

## 배치 레이어: Spark ALS 협업 필터링

### 협업 필터링이란

"나와 비슷한 관심사를 가진 사람들이 좋아한 기사를 나도 좋아할 가능성이 높다"는 원리입니다.

예시:
- 사용자 A: GPU, HBM, 반도체 기사를 자주 읽음
- 사용자 B: GPU, HBM 기사를 자주 읽고 "양자컴퓨팅" 기사도 읽음
- → 사용자 A에게 "양자컴퓨팅" 기사를 추천

### ALS (Alternating Least Squares)

Spark MLlib의 ALS는 암묵적 피드백(implicit feedback)에 특화된 행렬 분해 알고리즘입니다. 사용자가 "싫다"고 명시하지 않아도, 읽지 않은 기사를 암묵적 부정 신호로 활용합니다.

**학습 설정**:

| 파라미터 | 값 | 의미 |
|----------|-----|------|
| rank | 10 | 잠재 요인 수 (높을수록 복잡, 과적합 위험) |
| maxIter | 10 | 최대 반복 횟수 |
| regParam | 0.1 | 정규화 강도 (과적합 방지) |
| implicitPrefs | true | 암묵적 피드백 모드 |

### 실행 주기

매일 **새벽 3시** (Gold 파이프라인 완료 후) Airflow가 자동 실행합니다.

```
gold_serving (완료, ~새벽 2시)
      ↓
recommendation_als DAG (새벽 3시)
      ├── check_minimum_data  (사용자 5명 이상, 기사 10개 이상 확인)
      └── run_collaborative_filtering (Spark ALS Job)
```

최소 조건 미충족 시 Job이 SKIP됩니다. 서비스 초기(사용자 수 적을 때)에는 키워드 매칭만으로 동작합니다.

## 추천 점수 계산

두 레이어의 결과를 결합해 최종 순위를 매깁니다.

### ALS 결과가 있는 기사

```
최종 점수 = ALS 점수 × 0.4
           + 키워드 가중치 합 × 0.3
           + 최신성 감쇠 × 0.2
           + AI 분석 품질점수 × 0.1
```

### ALS 결과가 없는 기사 (키워드 매칭만)

```
최종 점수 = 키워드 가중치 합 × 0.5
           + 최신성 감쇠 × 0.3
           + AI 분석 품질점수 × 0.2
```

**최신성 감쇠**: 시간이 지날수록 점수가 낮아집니다.

```
최신성 점수 = e^(-0.01 × 경과시간(시간))
```

24시간 경과 시 약 0.79, 72시간 경과 시 약 0.49.

## 추천 이유 (reason 필드)

API 응답의 `reason` 필드로 이 기사가 왜 추천되었는지 알 수 있습니다.

| reason | 의미 | 활용 예시 |
|--------|------|-----------|
| `ALS` | 협업 필터링 기반 | "비슷한 관심사 독자들이 읽은 기사" |
| `KEYWORD_MATCH` | 관심 키워드 매칭 | "관심 키워드 기반 추천" |
| `COLD_START` | 데이터 부족 (신규 사용자) | "지금 인기 있는 기사" |

## 캐시 전략

| 캐시 항목 | 저장소 | TTL | 키 |
|-----------|--------|-----|-----|
| 뉴스 추천 결과 | Redis String | 30분 | `user:{userId}:recommendations` |
| 논문 추천 결과 | Redis String | 30분 | `user:{userId}:paper-recommendations` |
| 사용자 프로파일 | Redis Hash | 30일 | `user:{userId}:profile` |
| 트렌딩 키워드 | Redis Sorted Set | 무제한 (매일 50% 감쇠) | `search:trending` |
| 시간별 트렌딩 | Redis Sorted Set | 2시간 | `search:trending:{yyyy-MM-dd'T'HH}` |

추천 결과 캐시는 아래 이벤트에서 즉시 삭제되며, 그 외에는 TTL(30분) 만료 시 갱신됩니다.

| 이벤트 | 삭제되는 캐시 |
|--------|---------------|
| 기사 북마크 (`article-bookmark`) | 뉴스 + 논문 (프로파일 `kw:` 가중치를 공유하므로) |
| 북마크 삭제 (`DELETE /users/me/bookmarks/{articleId}`) | 뉴스 + 논문 (프로파일에 되돌릴 기록이 있을 때만) |
| 기사 조회 (`article-view`) | 뉴스 (체류 시간과 무관하게 매 요청마다 삭제) |
| 논문 조회 (`paper-view`) | 논문 (체류 시간과 무관하게 매 요청마다 삭제) |

관심사(`user_interests`) 추가·삭제는 Redis 프로파일에 반영되지 않으므로 피드에 영향이 없습니다(온보딩만 프로파일에 초기 키워드를 기록). 검색·온보딩처럼 프로파일이 바뀌지만 위 표에 없는 이벤트는 캐시를 삭제하지 않으므로 TTL 만료 후 반영됩니다. 조회 이벤트마다 캐시가 삭제되므로, 조회가 잦은 사용자는 피드가 매번 새로 계산됩니다.

**삭제 직후 재캐싱 방지**: 캐시를 삭제하는 이벤트는 삭제 대상 캐시마다 프로파일의 `rev` 값을 먼저 1 올립니다(`rev` 증가가 실패해도 캐시 삭제는 그대로 수행합니다). 추천을 계산하는 요청은 시작 시점의 `rev`를 기억해 두었다가, 결과를 저장할 때 Redis Lua 스크립트(`resources/redis/cache_if_profile_unchanged.lua`)로 "`rev`가 그대로일 때만 저장"을 **확인과 저장을 한 번에(원자적으로)** 수행합니다. 계산 중에 무효화가 발생했다면 `rev`가 달라져 있으므로 저장하지 않고 결과만 응답합니다. 프로파일 Hash 전체는 계산 1회당 한 번만 읽습니다. 스크립트 본문과 자바↔Redis 연결은 mock 단위 테스트로는 검증되지 않으므로, 실제 Redis 7에서 동작하는 통합 테스트(`RecommendationRedisIntegrationTest`, `AIRADAR_REDIS_IT=host:port`가 있을 때만 실행)와 `src/test/resources/redis/verify_cache_if_profile_unchanged.py`(fakeredis, 또는 `REDIS_URL`로 실제 Redis)로 검증하며, 스크립트 내용이 바뀌면 체크섬 테스트가 실패해 재검증을 요구합니다. 스크립트는 프로파일 키와 캐시 키를 함께 다루므로 Redis Cluster로 옮길 때는 두 키가 같은 슬롯에 있도록 해시 태그가 필요합니다 (현재는 단일 노드).

## Cold Start 문제와 온보딩

신규 가입자는 행동 데이터가 없어 추천 품질이 낮습니다. AI-Radar는 **온보딩**으로 이를 해결합니다.

가입 직후 관심 키워드를 1~10개 선택하면:
1. `user_interests` 테이블에 저장
2. Redis 프로파일에 즉시 반영
3. 키워드 매칭 추천이 바로 동작

온보딩 없이 `COLD_START`가 되면 전체 인기 기사만 보입니다.
